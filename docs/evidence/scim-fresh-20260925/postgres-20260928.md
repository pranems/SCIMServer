# PostgreSQL and InMemory: executable evidence

> **Last verified:** 2026-09-28
>
> **Source:** `ccde1d5d6b5129dd943c6e848989c668a0d00d7a`
>
> **Scope:** Analysis-only synthetic tests. No production code changes, live estate access, or repair.

## What this means in plain language

The earlier problem also happens with a **real PostgreSQL database**. It is not
just a limitation of the InMemory test backend.

* With strict validation **on**, the four-operation PATCH returns 400. The
  database payload, version, and GET ETag stay unchanged.
* With strict validation **off**, it returns 200. PostgreSQL stores the three
  intended Google updates, but leaves the real contact unchanged and stores an
  extra property literally named `contacts[primary eq true]`.
* Ordinary User, Group, and custom-resource CRUD journeys work in both backends
  for the tested inputs. The corpus also finds the earlier mutation and search
  problems in both.
* PostgreSQL is stronger in important places: its User uniqueness constraint
  rejects a competing duplicate, and its Group update transaction rolls back
  real database failures. InMemory does not provide those protections in the
  forced tests.
* PostgreSQL does **not** fix the application's version-check race. Two
  same-version writers can both succeed. The version check happens before the
  write rather than being part of one conditional database operation.

These are **77 finite cases per backend**, not a claim of full SCIM conformance.
A failing case is an unmet stated expectation, not necessarily one distinct bug.
Some cases deliberately inject a failure or control thread scheduling; those
are clearly marked below and in the data.

## Which storage claims now have runtime evidence?

1. **Conditional writes:** PostgreSQL still loses the same-version race. Both
   the plain HTTP sample and controlled overlap demonstrate it.
2. **User uniqueness:** PostgreSQL's real unique constraint is effective even
   when the service prechecks overlap. InMemory's precheck alone is insufficient.
3. **Group transaction rollback:** actual PostgreSQL transactions restore
   scalar fields, members, and version when member insertion fails.
4. **Group create partial persistence:** create and member insertion are not one
   atomic aggregate operation; both backends leave a Group after the injected
   member error.
5. **Endpoint cascade:** actual PostgreSQL foreign-key cascades remove the
   tested U/G/custom rows. InMemory removes endpoint access, not those records.
6. **Endpoint cache freshness:** a second warmed service instance can serve
   stale profile settings despite a changed PostgreSQL row. This does not prove
   every multi-process deployment behavior.
7. **Incident persistence:** the malformed key is in PostgreSQL JSONB, not only
   an in-memory working object or an incorrectly formatted response.

The eight result-difference cases are listed in `backendDifferences` in the
[summary JSON](postgres-20260928.summary.json). Three are plain wire concurrency
samples; the remaining differences concern uniqueness, native member constraint,
member failure rollback, cascade, and cache applicability. Do not infer parity
from the two backends having the same total number of failing cases.

## Test method and limits

The corpus uses production controllers/services/repositories through the
existing Nest HTTP test bootstrap. Every `stored()` check in the Prisma lane
also fetches the row from `PrismaService.scimResource` and verifies repository
payload/version against the actual JSONB row.

The deterministic race tests wrap only the pre-write repository method to
pause two requests until both arrive. They then call the **original method**.
No fake query result or mock database is returned.

Fault modes are deliberately different from ordinary traffic:

* Native rollback passes duplicate members directly to the real repository.
  PostgreSQL's actual unique constraint is the failure source.
* HTTP failure probes create a task-only trigger that raises during member
  insertion on the targeted synthetic aggregate/endpoint. The trigger/function
  is removed in `finally`.
* InMemory has no SQL constraints/triggers, so the matching HTTP probe throws
  at its member-insertion seam. This is labeled fault injection, not native SQL
  behavior or a normal request.

Not exercised:

* live estate replay, production repair, or migration of existing data;
* credential-row cascade, the authentication-method matrix, Bulk or `/Me` in
  this new dual-backend corpus;
* a full two-process cache deployment or load/performance percentiles;
* all possible attribute/characteristic combinations or filter grammar;
* transaction isolation under arbitrary external writers or multi-node load.

The existing 974 unit / 179 HTTP results from the earlier analysis were not
rerun or relabeled as PostgreSQL results. This corpus supplies new, independent
PostgreSQL evidence. Its expected behavior failures remain unfixed.

## Execution issues and assurance

| Issue | Resolution / evidence consequence |
|---|---|
| Container-tool configuration helper failed twice | Used the explicitly requested Docker CLI; verified its actual server version and installed image. No tool denial was bypassed |
| API dependencies and generated client absent after prior cleanup | A real `MODULE_NOT_FOUND` occurred first. Reused only the existing installed API dependency directory, generated Prisma client from pinned source, and did not change manifests or lockfiles |
| Disabled custom PATCH was initially masked by a separate required-ETag rejection | Added `CUSTOM-PATCH-DISABLED` with no masking precondition. It proves the mutation is accepted despite disabled PATCH, rather than treating any 4xx as capability enforcement |
| Extension typed read-filter failures could have been overgeneralized | Added `TYPED-READ-CONTROL`; core Boolean/compound and custom numeric comparisons pass |
| Plain races depend on scheduling | Kept plain results labeled as one sample; added deterministic pre-write barriers that still use the real storage |
| A credential-pattern check flagged the runner's `${password}` URL-construction template | The match was source code constructing a random in-memory value, not a saved credential. Checked persisted JSON/CSV/log excerpts separately and reviewed the source's environment passing and redaction; no actual password was persisted |

There were **zero setup failures** in the 154 recorded case executions.
The runner returns success only when both lanes wrote the full selected case
inventory, no setup failures occurred, migration replay completed, and cleanup
succeeded. The internal Jest runs return nonzero for the recorded unmet
expectations. Orchestrator success means **evidence collected safely**, not
“the server passed conformance.”

Safety negative controls rejected missing backend, missing task-container
identity, and an arbitrary InMemory database URL **before database access**.
Harness syntax, evidence counts, JSON, CSV alignment, documentation links,
and final cleanup are recorded in [validation](postgres-20260928.validation.json).

**Test/gate self-improvement:** applied through persisted-value checks,
deterministic real-storage barriers, explicit fault labels, and setup-failure
classification. **Design disposition:** no production redesign was made.
These results support separating application mutation semantics from atomic
repository guarantees, without claiming that a shared storage backend itself
fixes protocol logic.
